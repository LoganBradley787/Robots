## Vision
- A 2D side-view physics sandbox in the spirit of Bad Piggies, but with far more control.
- You build robots from grid parts in an editor, save them as blueprints, and spawn them into a world.
- You drive robots with keybinds and custom scripts, like MechJeb in Kerbal Space Program.
- Robots can be blown apart.
- Later phases (NOT now, but the architecture must support them):
  - AI-controlled robots.
  - Claude building robots from text.
  - Evolution and mutation of robot designs.

## Tech stack (decided; challenge it if you see a real problem)
- Browser, TypeScript.
- Physics: Rapier 2D (WASM), with deterministic mode enabled. Determinism matters for replays and later evolution.
- Rendering: PixiJS.
- Build tooling: your call (Vite is the default suggestion).
- Rejected alternatives:
  - Unity: editor-GUI-heavy, so AI can't do the plumbing; YAML scene files; nondeterministic physics.
  - Godot: viable, but AI often confuses the Godot 3 and 4 APIs.
- Possible Tauri desktop wrapper much later.

## Parts system (data-driven; this is the key modularity requirement)
- Every part type is a data definition, not special-cased engine code. It includes:
  - mass
  - footprint on the grid
  - attachable faces
  - rotation support (0/90/180/270)
  - health (see Destruction)
  - power draw when active
  - control channels it accepts (inputs)
  - sensor outputs it provides
  - sprite and animation info
- Adding a new part later (heat seeker, fuel cell, rotator) should mean adding a definition plus, at most, a small behavior module.

### Starting part set
- **Core:** black square. The controllable brain. Required for a robot to be controllable.
- **Frame:** gray square. Structural.
- **Battery:** green square. Has capacity.
- **Wheel:** black circle with a gray rectangle marking where it attaches. Motorized joint; takes speed input from -1 to 1.
- **Thruster:** gray rectangle. An orange flame rectangle appears in the firing direction when active. Takes throttle from 0 to 1 and applies force at its position.
- **Propeller:** lift force scaled by throttle. Do NOT physically rotate it; use a few-frame spin sprite animation (motion-blur frame at high speed) with playback speed tied to throttle.
- **Decoupler:** a detach point. Firing it splits the assembly.
- **Sensor parts:** pending an open question (see below).

## Physics structure
- A robot is a graph of grid cells.
- All welded cells in a connected set form ONE compound rigid body. Do not glue individual blocks together with weld joints; that causes sag, jitter, and explosions.
- Moving parts (wheels, propellers if needed) connect via joints.
- Center of mass comes from part masses automatically, so weight distribution matters.
- Mass limits: not now, but keep room for a world setting.

## Connectivity, destruction, and splitting
- After ANY cell removal (explosion, damage, decoupler), re-run connectivity (flood fill over attached faces).
- Each resulting connected chunk becomes its own rigid body, keeping its momentum.
- Explosions: remove every cell within a radius of 3 tiles, then re-run connectivity, then apply an outward impulse to debris.
- Health: every part has a health field from day one, even if all parts start at 1 HP (one-hit destruction). This avoids a refactor when armor or damage falloff is added later.
- More advanced explosion and damage models come later; keep the explosion logic pluggable.

## Cores, control ownership, and headless chunks
- A robot is controllable only through a core. The player can switch between any robots in the world that have a live core.
- Scripts live on the core.
- **Core destroyed, or chunk split off without a core:**
  - Every actuator in that chunk LATCHES its last command and keeps doing it (thruster stays at its throttle, wheels keep spinning).
  - Scripts no longer run for that chunk, and nothing new can be commanded.
  - The chunk keeps running only while its own batteries have charge.
  - This intentionally enables dumb missiles: angle the robot, turn the missile's thruster on, fire the decoupler, and it flies straight.
- Guided missiles are sub-assemblies with their own core.
  - While attached, the sub-core is dormant.
  - On detach, it wakes and runs its own script.
- Multi-core ownership rules: see open questions.

## Power (battery only for now)
- There is no fuel. Everything electric runs from batteries.
- Batteries have capacity. Active actuators drain at their declared rate.
- All batteries in a connected chunk share one pool. When a robot splits, each chunk keeps only the batteries physically in it (this falls out of connectivity).
- Empty pool means actuators stop.
- Implement this as a generic resource system with "energy" as the first resource, so fuel can be added later without refactoring every part.

## Control system (three layers)
1. **Channels:** parts expose named inputs (throttle, wheel speed) and outputs (sensor readings). Everything controls parts only through channels.
2. **Bindings (no code):**
   - Arbitrary user-defined keybinds, as many as wanted: "hold A: wheels -1", "F: toggle propellers."
   - Parts can be tagged into groups (for example, "outer props") and bindings can target groups.
   - Simple things like "A and D spin all wheels left and right" must be trivially easy.
3. **Scripts:**
   - JavaScript, running every fixed tick.
   - Scripts read sensors and key states, and write channels.
   - Keys can toggle scripts on and off (for example, H toggles a hover script).
   - Example: a hover script reads vertical velocity and adjusts propeller throttle to hold altitude.

### Arbitration
- A held manual binding overrides a script on the specific channels it touches, only while held.
- Scripts can also read key states directly and blend input in. For example, hover reads A and D to tilt smoothly instead of being hard-overridden. Support both.

### Input sources must be pluggable
- Keyboard is one source of virtual button presses and channel writes.
- A future AI core is another source using the same interface: it presses virtual buttons and runs full subroutines. An AI core cannot be driven by a human, but the player can still switch to view it.
- Design this interface now so the AI core is a small addition later.

## Scripting runtime
- Sandboxed JavaScript: a fixed tick rate, a time budget per tick, and a buggy script must never freeze the game.
- Scripts can declare tunable parameters (for example, hover gains), shown in the UI as sliders. Later, evolution mutates parameters and layouts, never script code.

## Sensors
- The game can provide perfect position, velocity, and acceleration data (unrealistic, intentionally).
- Whether these come from sensor parts or from the core: see open questions.

## Blueprints and the editor
- The canonical blueprint format is JSON: parts, positions, rotations, groups, bindings, scripts, and script parameters.
- There is a drag-and-drop editor. Save, load, and spawn blueprints into the world so robots never need rebuilding from scratch.
- Blueprints can reference sub-assembly blueprints (for example, "missile x4").
- The same format serves three consumers: the human editor, Claude, and later mutation.

## Claude-buildable robots (build the hooks early; this speeds up development a lot)
- Goal: I say "build me a drone with missiles" and Claude produces a working blueprint in about 90 seconds instead of my 1.5 hours.
- **ASCII blueprint view,** readable and writable by AI: a text grid plus a legend (symbol to part type and rotation), then bindings and script. For example:
```
  .  P  .  .  P  .
  F  F  C  B  F  F
  W  .  .  .  .  W
```
- **Validator** with precise, actionable errors, like "wheel at (0,2) has no attached face."
- **Headless test runner:** spawn a blueprint, simulate N seconds, and report metrics (altitude, tilt, battery remaining, distance). Claude can then build, test, and iterate without me.
- Mirroring and symmetry helpers are a nice-to-have.

## Assets
- PNG image assets, not SVG or procedural vector graphics.
- Simple placeholders generated by a script are fine for now (colors as described in the parts list).
- All sprites go through one texture manifest, so real art can be swapped in later by replacing files.

## Explicitly deferred (keep the architecture open for these)
- Heat-seeking sensors (idea: thrusters emit heat and seekers lock onto it).
- Fuel as a second resource.
- A precise rotation mechanism: a rotator or hinge part with a target angle, so a missile can be held and aimed before launch.
- Advanced explosion and damage models; armor.
- Materials, costs, or a crafting economy (it's a sandbox for now).
- Mass limits.
- AI core, Claude-in-the-loop building, and evolution/mutation.

## Open questions (ask me these; add your own)
1. **Multi-core:** when the active core dies and a dormant core in the same chunk survives, does it take over control, or does the chunk go headless (latched)?
2. **Sensors:** physical parts with mass and power draw (so sensing becomes a building decision), free data from the core, or the core has basic built-ins plus optional sensor parts?
3. **Controls UI:** keyboard binds only, or also a clickable on-screen button panel? (Suggestion: both, with the panel showing current binds.)
4. **Multi-tile parts:** is every part exactly 1 tile, or can some span several (a big 3-wide propeller)?
5. **Rotation and aiming:** what's the minimum mechanism for aiming a missile before launch? Could a rotator part come earlier than planned?
6. **World and terrain:** not discussed yet. Flat ground, hills, a terrain editor, obstacles and targets? What's the first test world?
7. **Scale:** tile size in world units, gravity strength, and how heavy parts feel relative to thrust.
8. **Camera and time:** follow the active robot? Zoom? Pause and slow motion (very useful for watching explosions and debugging scripts)?
9. **Persistence:** where blueprints are saved (browser storage, files, or both).
10. **Scripting API surface:** what exactly scripts can read and write, including other robots' positions (needed later for targeting).

## Suggested milestone shape (refine it; don't treat it as final)
- **M0:** Rapier plus PixiJS world with ground, gravity, and a falling box. Deterministic stepping and a camera.
- **M1:** Part definitions, grid assembly into compound bodies, wheels on joints.
- **M2:** Editor: place, rotate, and delete parts; save, load, and spawn blueprints.
- **M3:** Channels plus keybinds and groups. Drive a car.
- **M4:** Power system and batteries.
- **M5:** Script runtime with toggles, arbitration, and parameters. A working hover drone.
- **M6:** Destruction, connectivity splitting, decouplers, latching headless chunks. Dumb missiles.
- **M7:** ASCII blueprint format, validator, and headless test runner. Claude builds robots from text.
