# Rapier 2D (JavaScript/WASM) for the robot sandbox

Research notes, 2026-09-22. Verified against the npm registry, the shipped 0.20.0 tarballs (`rapier.d.ts` per module), the merged repo (https://github.com/dimforge/rapier/tree/master/typescript), rapier.rs docs, docs.rs, and Node 24 spikes run on an Apple M3 Pro. "Verified" below means I ran it; "docs" means quoted from a source.

## 1. Packages and versions

- All six 2D packages are at **0.20.0**, published 2026-08-08: `@dimforge/rapier2d`, `-compat`, `-deterministic`, `-deterministic-compat`, `-simd`, `-simd-compat` (registry: https://registry.npmjs.org/@dimforge%2Frapier2d etc.). A `canary` dist-tag (`0.0.0-<sha>-<date>`) carries unreleased soft-body work with breaking API changes (repo CHANGELOG "Unreleased"): pin `0.20.0`.
- 0.20.0 wraps Rust rapier 0.35.x (build template pins `rapier2d = 0.35.0`, `parry2d = 0.31`: https://github.com/dimforge/rapier/blob/master/typescript/builds/prepare_builds/templates/Cargo.toml.tera). npm and crate versions are intentionally different numbers (https://github.com/dimforge/rapier/issues/997).
- Variants, per the package README template (https://github.com/dimforge/rapier/blob/master/typescript/builds/prepare_builds/templates/README.md.tera):
  - base: default build, "no cross-platform determinism guarantee (but it is still locally deterministic, on the same machine)".
  - `-simd`: built with `RUSTFLAGS='-C target-feature=+simd128'` and `wasm-opt --enable-simd`; "requires support for simd128" in the browser.
  - `-deterministic`: built with the cargo feature `enhanced-determinism`; "less optimized build but with a guarantee of a cross-platform deterministic execution". Feature mapping is in https://github.com/dimforge/rapier/blob/master/typescript/builds/prepare_builds/src/main.rs.
  - `-compat` of each: the `.wasm` is embedded as base64 inside `dist/rapier.mjs` and `dist/rapier.cjs` (2.1 MB each on disk, about 0.8 MB gzipped); `package.json` has an `exports` map with `import`, `require`, and `types`. You must `await RAPIER.init()` first. 0.20.0 moved compat files into `dist/` and fixed how the embedded module is passed to `init()` (CHANGELOG: https://github.com/dimforge/rapier/blob/master/typescript/CHANGELOG.md).
- Non-compat packages ship a separate 1.49 MB `.wasm` and use extensionless ESM imports plus `import * as wasm from "./rapier_wasm2d_bg.wasm"`. Plain Node fails with `ERR_MODULE_NOT_FOUND` (verified), and native browser ESM fails the same way (https://github.com/dimforge/rapier.js/issues/348). Vite needs `vite-plugin-wasm`, `vite-plugin-top-level-await`, and `optimizeDeps.exclude: ['@dimforge/rapier2d']` (https://github.com/dimforge/rapier.js/issues/49, https://github.com/Menci/vite-plugin-wasm/issues/8).
- Verified: all three `-compat` variants load in Node 24 by ESM `import` and by CommonJS `require()` with no flags, and Vite consumes them with no plugins (they are plain JS). The same build in browser and Node is the only way to get identical numbers, because the three builds are separate WASM binaries.
- **Recommendation: `@dimforge/rapier2d-deterministic-compat@0.20.0` everywhere** (Vite app, Node/Vitest headless runner). Measured speed cost versus base was small (section 9).

## 2. Determinism

- Rust guide (https://rapier.rs/docs/user_guides/rust/determinism): Rapier is "locally deterministic" by default (same machine, same build); cross-platform determinism needs the `enhanced-determinism` feature, strict IEEE 754-2008 targets (WASM qualifies), and deterministic inputs. `enhanced-determinism` enables `simba/libm_force` and `parry2d/enhanced-determinism` (https://github.com/dimforge/rapier/blob/master/crates/rapier2d/Cargo.toml). WASM is single-threaded, so parallel reduction order is not a factor.
- JS guide (https://rapier.rs/docs/user_guides/javascript/determinism) says the WASM build is "fully cross-platform deterministic" and mentions `world.createSnapshot()`. That page predates the package split: the method is `takeSnapshot()`, and only the `-deterministic` build carries the guarantee per the README. Its user-side rule still holds: "transcendental functions like Math.sin, Math.cos are not cross-platform" deterministic, so do not derive initial state from them.
- Verified, same build run twice: identical per-body state hash and identical snapshot MD5 (base, deterministic, simd each). Verified across builds: body states were bit-identical for 600 steps in a scene with contacts, a motorized revolute joint, and persistent forces, yet snapshot bytes differed between builds in one scene and matched in another. Compare state hashes, or snapshots from the same build; do not compare raw snapshot bytes across builds.
- Caller obligations: constant `world.timestep` (docs: a timestep "should not vary too much"); same sequence of create/remove calls (handles are arena index + generation, so allocation order fixes handle values and reuse); same integration parameters; a seeded PRNG; no wall-clock or frame-rate dependent branching; iterate your own containers in insertion order (JS Map/Set already do); consume events in drained order. Scene query callbacks are ordered by the internal BVH, which is itself a function of the operation sequence.
- Open issue https://github.com/dimforge/rapier/issues/797: determinism loss after `setRotation` / `setRotationWrtParent` following `restoreSnapshot`, reported on 0.14 through 0.19.2, and in production with `-deterministic-compat` 0.18.1. On 0.20.0 my test (6 runs of restore, `setRotation`, `setRotationWrtParent`, 300 steps) produced a single hash. Still: set poses through `RigidBodyDesc` at creation where possible, and hash-test any code path that mutates poses after creation.
- Snapshots exist in JS: `world.takeSnapshot(): Uint8Array` and static `RAPIER.World.restoreSnapshot(bytes): World` ("an identical copy", d.ts). Verified: restore then `takeSnapshot` gives byte-identical output; handles are preserved. Cost per https://github.com/dimforge/rapier/issues/991: about 1 KB per body, 0.035 ms at 50 bodies, 0.4 ms at 800 bodies, and about 1 MB of GC churn per call at 800 bodies.
- Snapshot caveats: `userData` is not serialized (verified: restored body has `userData === undefined`), so keep a side table keyed by handle and reattach. The `EventQueue` is separate and not part of the snapshot. `restoreSnapshot()` leaks about 1.7 KB of WASM memory per call even after `free()` (https://github.com/dimforge/rapier/issues/990, filed against 0.20.0): fine for save/load, budget for it in replay verification loops.

## 3. Compound rigid bodies

- API confirmed in `dynamics/rigid_body.d.ts` and `geometry/collider.d.ts`: `RigidBodyDesc.dynamic().setTranslation(x, y).setRotation(angle).setLinvel(x, y).setAngvel(w)`; `world.createRigidBody(desc)`; `ColliderDesc.cuboid(hx, hy)` (half extents) `.setTranslation(x, y).setRotation(angle).setMass(m)` or `.setDensity(d)` or `.setMassProperties(mass, localCom, angularInertia)`; `world.createCollider(desc, body)`.
- `setMass`: "The angular inertia of this collider will be computed automatically based on its shape and this mass value" (d.ts). Body mass, centre of mass, and inertia are the sum over attached colliders plus any additional mass. Verified: a 3x3 grid of 0.5 m cells with masses 1..9 gives `mass() = 45`, `localCom() = (0.567, 0.700)`, `principalInertia() = 14.875`.
- Runtime add: `createCollider(desc, body)` updates `mass()` and `localCom()` immediately (verified). Runtime remove: `removeCollider(c, true)` does **not** update them until the next `step()` or an explicit `body.recomputeMassPropertiesFromColliders()` (verified: 45 stayed 45, then 44 after recompute). Always recompute after removals before reading mass or COM in the same tick.
- Zero colliders left: `mass()` is 0, the body ignores gravity and forces and goes to sleep, no crash (verified). Docs: "If the rigid-body has no collider attached to it, its mass will be zero unless you gave it a mass (or mass properties) explicitly" (https://rapier.rs/docs/user_guides/javascript/common_mistakes). Remove such bodies yourself.
- Do not use `setAdditionalMass` on chunk bodies: it is added on top of the collider sum at the body origin and distorts the automatic COM. A density-0 collider contributes nothing (d.ts). Values come back as float32 (`43.999996`), so compare with tolerance.
- Readers available: `mass()`, `invMass()`, `localCom()`, `worldCom()`, `principalInertia()`, `effectiveAngularInertia()`, `numColliders()`, `collider(i)`.

## 4. Splitting a body at runtime

- There is no `Collider.setParent` in the JS API (verified absent; the Rust `ColliderSet::set_parent` is not bound). Cleanest flow: for each new chunk, `createRigidBody` at the parent's current `translation()` and `rotation()` (so cell local offsets stay valid), `createCollider` a fresh `ColliderDesc` per cell from your own cell spec (offset, half extents, mass), then `removeCollider(old, true)` from the remainder, or `removeRigidBody(parent)` if nothing remains. Never destroy and rebuild the whole world for a split.
- Momentum: capture `oldCom = parent.worldCom()`, `v0 = parent.linvel()`, `w0 = parent.angvel()` **before** touching anything. For every chunk, including the remainder: `v = (v0.x - w0 * (com.y - oldCom.y), v0.y + w0 * (com.x - oldCom.x))`, `setLinvel(v, true)`, `setAngvel(w0, true)`. `RigidBody.velocityAtPoint(p)` computes exactly this (verified equal) but against the current COM, so call it before removal or do the arithmetic yourself.
- The trap: `linvel()` is the COM velocity. Removing colliders moves the COM while Rapier keeps `linvel` numerically unchanged, which silently changes the body origin's velocity (verified). My first attempt skipped the remainder and drifted total momentum from (90, -45) to (93.4, -54.7); with the correction, mass, linear momentum, angular momentum, and kinetic energy were conserved to 4 decimals across all three builds.
- Contacts: `removeCollider` drops that collider's contacts; nothing else to do. `removeRigidBody` "will remove this rigid-body as well as all its attached colliders and joints. Every other bodies touching or attached by joints to this rigid-body will be woken-up" (d.ts; verified `impulseJoints.len()` 1 to 0 and `joint.isValid() === false`).
- Joints anchor to bodies, not colliders. If the cell a joint was anchored on moves to a new chunk, you must remove the joint and recreate it on the new body; the local anchor is unchanged if the new body shares the parent's frame. Pass `wakeUp = true` on all of these calls.
- Stress on 0.20.0: 8,100 body/collider creations and 6,580 removals over 900 steps with no panic (verified). Older bindings crashed with `RuntimeError: unreachable` when creating colliders quickly (https://github.com/dimforge/rapier.js/issues/363, 0.18 to 0.19.3).

## 5. Joints

- `RAPIER.JointData.revolute(anchor1, anchor2)`: both anchors are "expressed in the local-space of the rigid-body" (d.ts). `world.createImpulseJoint(params, body1, body2, wakeUp)` returns `ImpulseJoint`; cast to `RevoluteImpulseJoint` (verified `instanceof`). Docs: https://rapier.rs/docs/user_guides/javascript/joints
- Motor API on `UnitImpulseJoint` (d.ts): `configureMotorModel(MotorModel.AccelerationBased | ForceBased)`, `configureMotorVelocity(targetVel, factor)`, `configureMotorPosition(targetPos, stiffness, damping)`, `configureMotor(targetPos, targetVel, stiffness, damping)`, `setMotorMaxForce(maxForce)`, `setLimits(min, max)`, `limitsEnabled()`, `setContactsEnabled(false)` to let jointed parts overlap.
- Semantics from the Rust source (https://docs.rs/rapier2d/latest/src/rapier2d/dynamics/joint/generic_joint.rs.html): velocity motor sets `stiffness = 0, damping = factor`; position motor sets `targetVel = 0`; `max_force` defaults to `Real::MAX` (unlimited). `MotorModel::AccelerationBased` (default): `acceleration = stiffness * err + damping * velErr`, mass independent; `ForceBased`: same formula yielding a force/torque (https://docs.rs/rapier2d/latest/rapier2d/dynamics/enum.MotorModel.html).
- Verified: `configureMotorVelocity(20, 1.0)` on a free wheel adds 0.333 rad/s per step (20 rad/s^2 x 1/60), so in AccelerationBased the `factor` is a gain in 1/s. `setMotorMaxForce(0.5)` on inertia 1.25 gave 0.0067 rad/s per step (0.5 / 1.25 / 60): the cap is a torque in N m even under the acceleration model. Wheels: `configureMotorVelocity(targetOmega, 10..60)` plus `setMotorMaxForce(maxTorque)`; use `ForceBased` if you want the motor's strength to depend on the load.
- Position motor (rotator parts), verified: with AccelerationBased, critical damping is about `2 * sqrt(stiffness)`. Stiffness 50 / damping 5 overshoots a 1.0 rad target to 1.51 rad and oscillates; 500 / 50 settles at 1.001 rad within about 40 steps. Add `setMotorMaxForce` to stop huge corrections when a target is far away.
- Removal: `world.removeImpulseJoint(joint, wakeUp)`; joints die automatically with either body (section 4). Use `joint.isValid()` before touching a cached joint.

## 6. Forces

- `addForce(f, wakeUp)`, `addForceAtPoint(f, worldPoint, wakeUp)`, `addTorque(t, wakeUp)` are **persistent and additive** across steps. Docs: "Added forces are persistent across simulation steps, and can be cleared manually" (https://rapier.rs/docs/user_guides/javascript/rigid_bodies). Verified: calling `addForceAtPoint({0, 30})` for 600 steps left `userForce() = (0, 18000)`.
- Thruster pattern per tick: `body.resetForces(false); body.resetTorques(false);` then add this tick's forces, then `world.step()`. Or use one-shot `applyImpulse` / `applyImpulseAtPoint(force * dt, worldPoint, wakeUp)` each tick. `addForceAtPoint` off the COM also produces torque. `userForce()` / `userTorque()` let you inspect the accumulator. Sleeping bodies ignore forces unless `wakeUp = true`.

## 7. Scale and tuning

- Units are SI: metres, kilograms, seconds, radians; gravity `{ x: 0, y: -9.81 }` (getting started: https://rapier.rs/docs/user_guides/javascript/getting_started_js). Docs warn that treating pixels as metres yields 100 m bodies that fall in "slow motion"; render with a pixels-per-metre factor (docs example: 50 px per metre) (https://rapier.rs/docs/user_guides/javascript/common_mistakes).
- `world.lengthUnit` = "the approximate size of most dynamic objects in the scene" (d.ts, default 1). Internal tolerances scale with it: measured `normalizedAllowedLinearError = 0.005` and `normalizedPredictionDistance = 0.02` (the d.ts docstring still says 0.002), plus sleep thresholds. Practical rule: keep typical parts at or above about 0.1 m and below tens of metres, or set `lengthUnit` to your typical part size. A 0.25 to 0.5 m grid cell at `lengthUnit = 1` is comfortable; a 0.05 m cell is not. Keep mass ratios within a joint chain under roughly 1000:1.
- 60 Hz: `world.timestep = 1 / 60` (the default), never varied. Measured 0.20.0 defaults: `numSolverIterations 4`, `numInternalPgsIterations 1`, `maxCcdSubsteps 1`, `contact_erp 0.136` (derived from `contact_natural_frequency`). Exposed on `World`: `timestep`, `numSolverIterations`, `numInternalPgsIterations`, `maxCcdSubsteps`, `lengthUnit`, and `integrationParameters` (`dt`, `contact_erp`, `contact_natural_frequency`, `normalizedAllowedLinearError`, `normalizedPredictionDistance`, same iteration fields). `numAdditionalFrictionIterations` is not exposed in JS; the JS integration-parameters guide page is stale (it still lists `max_velocity_iterations`).
- For stacked, jointed robots: try `numSolverIterations = 8`, or `numInternalPgsIterations = 2..4` (d.ts: "lesser effect than increasing numSolverIterations but is also less computationally expensive"). Enable `setCcdEnabled(true)` only on small fast bodies. Rapier 0.35 changed sleeping and CCD defaults ("sweep-based CCD now enabled by default", CHANGELOG), so tune against 0.20.0, not older examples. If a case is still unstable, run two `step()` calls at `dt / 2` rather than piling on iterations.

## 8. Collision events and queries

- Events: `const eq = new RAPIER.EventQueue(true)` (`autoDrain`, d.ts recommends `true`); `world.step(eq)`; `eq.drainCollisionEvents((h1, h2, started) => ...)` needs `ColliderDesc.setActiveEvents(RAPIER.ActiveEvents.COLLISION_EVENTS)` on at least one collider of the pair; `eq.drainContactForceEvents(e => ...)` needs `ActiveEvents.CONTACT_FORCE_EVENTS` (value 2; OR the flags for both) and `setContactForceEventThreshold(newtons)` (default 0 reports every contact). Guide: https://rapier.rs/docs/user_guides/javascript/advanced_collision_detection
- `TempContactForceEvent` exposes `collider1()`, `collider2()`, `totalForce()`, `totalForceMagnitude()` ("sum of the magnitudes of each force", d.ts), `maxForceMagnitude()`, `maxForceDirection()`. The object "should not be stored anywhere"; read it inside the callback. Verified: a 45 kg compound landing produced 141 events over 120 steps with threshold 50 N and a peak `totalForceMagnitude` of 3,517 N. Use `maxForceMagnitude()` for impact damage; multiply by `dt` if you want an impulse.
- Per-point contact data: `world.contactPair(c1, c2, (manifold, flipped) => ...)`, `world.contactPairsWith(c, c2 => ...)`.
- Radius query for explosions: `world.intersectionsWithShape(center, 0, new RAPIER.Ball(r), collider => { ...; return true; }, filterFlags?, filterGroups?, excludeCollider?, excludeRigidBody?, predicate?)` (d.ts; return `false` to stop). Verified: returns each collider whose shape overlaps the ball. Coarse alternative: `world.collidersWithAabbIntersectingAabb(center, halfExtents, cb)`. Guide: https://rapier.rs/docs/user_guides/javascript/scene_queries
- User data: `RigidBody.userData` exists (`RigidBodyDesc.setUserData`), **`Collider` has no `userData`** (verified). Map parts with `Map<ColliderHandle, PartId>` keyed by `collider.handle`, and go back with `world.getCollider(handle)`, `collider.parent()`, `world.getRigidBody(handle)`. Handles are `number`s carrying index + generation in the raw f64 bits (they print as `2.1e-314`): treat them as opaque, never round or add, and purge map entries on removal because slots are reused with a new generation.

## 9. Performance in the browser

- Measured in Node 24 (V8, same engine as Chrome) on an M3 Pro, 3,000 awake 1 m boxes falling into a bin: base 2.3 ms/step, deterministic 2.0 ms, simd 1.7 ms; once asleep the step is about 0 ms. A 2,000-box pile averaged 1.7 / 1.3 / 0.8 ms per step over 180 steps. Creating a body plus collider cost about 5 microseconds, removing one about 1.5 microseconds (2,000 in 10 ms and 3 ms).
- External: Godot's Rapier 2D benchmark reports "roughly 9,000 active box-stack bodies fit in a 60 FPS physics budget" on an M1 (native, not WASM) and "sleeping bodies are nearly free" (https://godot.rapier.rs/docs/documentation/performance/). Joint-heavy scenes are the weak spot (joint grid: 6.4 ms Rapier vs 3.9 ms Box2D v3 there). A 2021 browser test held 7,500 active bodies at 60 FPS (https://dev.to/jerzakm/this-little-known-javascript-physics-library-blew-my-mind-57oo).
- Budget guidance: a few thousand awake colliders and a few hundred motorized joints fit in a 16 ms frame at defaults; compound bodies keep the solver-body count low (contacts scale with colliders, joints with bodies). Snapshotting every frame is the expensive part (section 2). `RAPIER.reserveMemory(bytes)` pre-grows WASM memory to avoid growth pauses.

## 10. Other things to know

- Init: `import RAPIER from '@dimforge/rapier2d-deterministic-compat'; await RAPIER.init();` then `new RAPIER.World(gravity)`. `RAPIER.version()` returns `"0.20.0"`. Also works with `require()`.
- Memory: only long-lived wrappers need `.free()`: `World` ("all the fields of this physics world will be freed as well") and `EventQueue` ("MUST be freed manually"). Bodies, colliders, joints, vectors, and descriptors do not (CHANGELOG 0.7 rewrite notes). Each `restoreSnapshot` returns a new `World`: free the old one.
- TypeScript: complete per-module `.d.ts`. `tsc` 5.9 `strict` passes under `moduleResolution: "bundler"` and `"nodenext"` for the compat package (https://github.com/dimforge/rapier.js/issues/369 no longer reproduces), but the wasm-bindgen `.d.ts` uses `Symbol.dispose`, so add `"esnext.disposable"` to `lib` or set `skipLibCheck: true`. Quirks: 2D `Rotation` is a plain `number` (radians); `ColliderDesc.setTranslation(x, y)` vs `Collider.setTranslationWrtParent({x, y})`; snake_case leftovers (`contact_erp`, `rest_length`); a few stale docstrings.
- Open issues worth watching: https://github.com/dimforge/rapier/issues/985 (0.20.0 `RuntimeError: unreachable` in `step()` with `ConvexPolygon` plus ball; cuboids and balls were fine in my runs, so avoid convex polygons or test them), 990 and 991 (snapshot leak and size), 797 (`setRotation` determinism), 998 (static contact softness not exposed), 993 (voxel shapes). A WASM panic is an uncatchable-in-effect `RuntimeError: unreachable` that leaves the `World` unusable: wrap `step()` in try/catch and rebuild from the last snapshot.
- Docs drift: `dimforge/rapier.js` is archived (merged into `dimforge/rapier/typescript`, July 2026); the JS user guide still references 0.17 and old integration parameters. Trust the shipped `.d.ts`, the repo CHANGELOG, and the docs.rs sources for 0.35 over the JS guide pages when they disagree.
- Handles, `userData`, and event queues are the three things that do not survive a snapshot boundary in your own bookkeeping; design the part registry so it can be rebuilt from `world.forEachRigidBody` plus a handle-keyed table.
