# 10 Builder

Status: decided with Logan, 2026-09-23 (before the M2 plan). Supersedes the M2 bullets in `06` where they differ.

## Why a separate screen
Logan: building is more than dragging pieces. Later it means scripts and sensor logic (a heat-seeking missile has to read sensors and correct for gravity). Doing that inside the world is cramped and awkward, and redoing it every time is worse. So blueprints are designed once in a dedicated builder, saved, and deployed.

## Screens
- Two screens: the world and the builder. `Tab` flips between them. The world keeps its robots and is paused while the builder is open.
- The app opens in the builder on a blank blueprint. The world starts with terrain only.
- Builder look: dark blue background with a laid-out grid (exact look is Claude's call, judged at Gate 2).

## Blueprints and files
- Blueprints are files in the repo's `blueprints/` folder, read and written through a small dev-server endpoint. Claude reads what Logan builds and Logan opens what Claude writes. Git keeps history.
- A dropdown lists every blueprint. The builder starts on a blank one; picking one opens it.
- Saving is explicit (Logan's call, overriding autosave): **Save** overwrites the open blueprint's file. **Save As** asks for a name and writes a new file; the original stays unchanged. Reason, in Logan's words: open the aircraft carrier, delete everything but one missile to try something, deploy it, and autosave would have destroyed the carrier.
- Unsaved changes are never lost silently: switching blueprints or starting a new one with unsaved changes asks **Save / Don't save / Cancel**. "Don't save" keeps the file as it was and discards the edits. Test has its own small box (M16, see Test below).
- (M16) The strip across the top has the file actions as buttons of their own: **New**, **Open**, **Save**, **Save as**, **Delete** (Save as and Delete were in a menu; the strip has the room). New and Open ask about unsaved changes, Delete asks first, as before.
- **Delete** (it was Delete file) removes the blueprint's file and the script files named after it (`drone.hover.js` for `drone.json`: the ones Save and Save As wrote for it), and says so before it does. A script file named after it that another saved blueprint uses too stays, and the box says which robot uses it (`enemy-fab-gun-drone` loads `enemy-fab-drone.missile-up.guide.js`). What is on screen stays, as an unsaved blueprint.
- Files are written in the grid form when it can express the blueprint (readable for Claude and in diffs), else the `parts` form. Two parts on one cell is one of the things a grid cannot express (it would write one and lose the other), so such a blueprint is written in the `parts` form with both, and the issues list names the overlap (review E1).

## The board: one way of working (M16)
There are no modes. What a click does depends only on whether something is in the hand; the hand chip, the ghost and the hint line always say which.
- **Hand full** (a tile from the drawer, a hotbar key `1` to `9`, `Alt`+click on a part, `Cmd/Ctrl+D` on a selection, a saved robot, or the eraser `E`): a click or a drag places on empty cells, and one drag is one undo step. `R` and `Shift+R` turn it, `F` flips a held robot or a held copy, `Esc` or a right-click puts it down.
- **A taken cell refuses a placed part**, and says why at the cursor for about two seconds. **Shift while placing swaps**: the part there gives way and the new one keeps its place in the robot, its groups and the settings that still apply (`replacePartAt`). The same part already standing there is not a refusal, so a drag can pass over what it painted.
- **Hand empty**: a click selects a part, `Shift`+click adds or removes one, a drag across empty cells selects a box (a part is in the box when any of its cells is, review E4), and a drag that starts on a selected part moves the selection: it follows as outlines and lands on release. Blocked, it says why at the cursor and nothing moves. Arrow keys nudge the selection one cell, `R` turns it (a turn onto another part is refused whole, review E1), `Delete` removes it, `Cmd/Ctrl+D` puts a copy in the hand, `Cmd/Ctrl+A` selects everything. A right-click selects a part and turns the inspector to it. `Esc` calls off a drag, then lets go of the selection.
- **A move keeps the part**: its groups and settings travel, its id follows its cell, and every key that named the old id follows it (`movePartsBy`). Script code is never rewritten; a script that spells the old id is named in the notice after the move.
- **Copies carry everything.** `Alt`+click holds a copy of that very part (type, turn, groups, settings) and `Cmd/Ctrl+D` a copy of the selection (`stampOfParts`, `placePartStamp`). A copy of part of a named assembly joins it. A copy that holds all of a named assembly (every part that carries `gun-turret1`, as the Assemblies tab and `pnpm sim place` name what they place) is one more of them: it lands as `gun-turret13`, and a copied core brings its keys and scripts under the new name, so a script that finds turrets by name drives the new one by itself.
- **A plain tile is blank.** When it lands touching parts of its own type that all share a group, the builder offers "Add to group X" at the cursor: one click, easy to ignore.
- **Mirror** (`M`) is a switch with its line drawn. A place, a Shift swap, a move or nudge, and an erase happen on both sides, or not at all: a place with one side taken is refused whole, and a move takes the mirror image of each selected part the other way in the same step.
- **Swap to** (Part tab, for parts of one type): pick another part from a small picker with search. The part keeps its place, turn, groups and the settings the new one has too. When a key or a script drove it by its type name, the new part keeps that name as a group (`keepTypeTag`), so they still reach it. A swap that does not fit is refused with the reason.
- **No warnings before an edit; a notice after it**, with Undo in it, that goes away by itself: what a swap kept and dropped and what will not work on the new part (an input it lacks, a script's own `p.type === 'x'` test, which a group cannot satisfy); what drove a removed part and which names reach nothing now; which scripts still spell a moved part's old id.
- Undo and redo (`Cmd/Ctrl+Z`, `Shift+Cmd/Ctrl+Z`) are whole actions: one drag, one move, one nudge, one swap, one accepted offer.
- The grid follows the view: the board has no edge.

## What a script drives (M16)
All of it reads names and inputs, never part types (`sim-core/src/script/reading.ts`).
- **Behaviors tab**: each script's card says what it drives ("Drives 12 parts"). Its **Show** switch lights the board: the parts it reaches by a name written in its code get a solid blue frame and the rest of the robot steps back. `Esc` with an empty hand puts the light out. Resting the mouse on a card lights nothing (it did until the cards came: it flickered as the mouse crossed the tab).
- **A script that builds names in code** (`name + '.gun'`) says so: "this script also picks parts in its own code, so this list may be incomplete". The parts whose group fits a name it builds get a dashed frame (`partsBuiltTargetsFit`): likely, not sure.
- **Not driven**: a part of a type the script drives through a group, in none of its groups, gets an orange dashed frame and a row under the script with "Add to group X" (one undo step). Nothing is listed for a script that builds names in code or names the type itself: it may reach the part that way.
- **Part tab**: each input says what drives it today: its auto key, your keys, and the scripts that write it (a click shows that script in the Behaviors tab).
- **Problems** lists names in scripts that reach nothing (`scriptNameIssues`, folded over copies of one script), as warnings with the script, the line and the real names. A click opens the script with that line selected. When a real name is a letter or two away it offers "Point it at X": the line as it is and as it would be, and only that exact quoted text at that exact place is rewritten, as one undo step. Spare names are not problems.

## Behaviors: the shelf and the cards (M16)
The shelf is the repo's `behaviors/` folder (`04`, Shared behaviors). The dev server serves it read only at `/api/behaviors`, beside the blueprint files, and it is read again each time the list is opened, so a file an agent just wrote is there. Like the blueprint files, it is there only under `vite dev`: nothing is bundled into a build.
- **Add a behavior** (Behaviors tab) lists the shelf: each behavior's name, its one line, and whether it can work on this robot (`fitBehavior`). One that cannot is greyed with the reason in plain words ("needs something with a fire input; needs something that sees, such as a radar"). **Write your own** starts a blank script, as before.
- **Choosing one fills its slots on the board, one at a time.** A banner over the board asks ("What lifts/pushes? These 4 parts look right.") with the guess already lit in green (never the yellow of the selection or the blue of a script's reach); the parts that could fill the slot have a thin dashed green frame and the rest of the robot steps back. A click on a part puts it in or takes it out; for a slot that takes many parts, **Select all** picks every part that could fill it and **Clear** picks none (each shows only when it would change something; the sentence then says "All 6 parts picked."). Select all is the way to take what the first guess leaves out on purpose: for the main core, the parts of a placed copy that has its own core. A part that cannot fill the slot is refused at the cursor with the reason ("A frame has no throttle input, so it cannot be "what lifts/pushes"."). **Accept** (`Enter`) goes on to the next slot, **Skip** leaves an optional slot as it was, **Back** returns to the slot before, **Cancel** (`Esc`) calls the whole thing off with nothing changed. A slot nothing on the robot could fill is not asked about. While a slot is being filled no other key or click edits the robot: nothing can be selected (on the board or in the inspector), and Swap to, Delete and the drawer wait. Finishing writes only picked parts that are still there and still fit the slot.
- **Finishing is ONE undo step**: the robot's own copy of the file is attached (marked `// @from hover 2 <sum>`), each slot's group is written on its parts, and parts a slot owns are taken off their auto keys. The notice says so: "Hover now drives 4 propellers. Their own keys are off."
- **A behavior's card**: its name and one line; "from the shelf, version N" (and "edited here" once the copy's text no longer has the check sum in its mark); **about** (the header's notes, the script's id and file); on at start; the key that switches it on and off (click the cap, press a key; `Backspace` takes it away; world keys are refused with the reason); each slot with what fills it ("2 propellers", a click selects them) and **change**, which reopens slot filling for that one slot (a part taken out of a slot that owned it gets its own keys back); each `param()` as a slider with its number beside it and the comment after its `param(...)` line as the words under it (one drag is one undo step; double-click for the default), except an on/off one (it runs exactly 0 to 1 from a default of 0 or 1, and is 0 or 1 now: Hover's `keys`, Aim and fire's `auto`), which is a switch and stays 0 or 1 in the blueprint (a 0 to 1 amount such as `reserve` 0.3 keeps its slider, and so does one set in between by hand); what it drives, with **Show**; **Edit code**; **Remove**.
- **Update**: when the shelf's `@version` is higher than the copy's, the card offers "update to N". It opens the copy set against the shelf's text (their `@from` lines left out), changed lines only with a few around them, and says whether the copy was edited on this robot: if so the lines in red are what would be lost. Update replaces the text as one undo step and keeps the settings, the key and the groups.
- **Remove** asks first, and for a behavior offers two ways: keep the groups its slots filled, or clear them, which also gives the parts it drove their own keys back. A group another script still names, or a key of this core targets, is never cleared, and a part another behavior's slot still owns keeps its own keys off (that one drives it). The same goes for a part taken out of a slot with **change**.
- **An ordinary script** (no behavior header) gets a plainer card: its name (editable), its file, on at start, its key, its params as sliders, Show, Edit code, Remove.
- A copy is saved with the blueprint exactly as other scripts are (`drone.hover.js`); the slots are groups on the parts and the mark is a line of the copy, so Save, Save As and opening the robot again need nothing new.

## The script view (M16)
The Script button, or Edit code on a card. It lies over the parts drawer and the left of the board; a strip of board stays in view beside the inspector, with the robot shown whole in it (about 316 px wide at 1366 by 768). **Done** closes it and puts the board's view back where it was.
- **The code** is in the middle: CodeMirror 6 with JavaScript colours in the Shop floor tokens, line numbers, bracket matching, find (`Cmd/Ctrl+F`), its own undo while typing, and long lines wrapped. To the builder, one visit to the text is one undo step. `Esc` closes a completion or the find bar and never lets go of the text (the next letters would be the board's keys).
- **This robot** (left column): every group, kind of part and single part a script of this core can name, groups first, each with its inputs (name, range, what the ends mean) and what it reports. A click writes the call at the caret: `set("lift", "throttle", )` with the caret where the value goes, or `get("battery", "charge")`. For a placed copy's own core the list is its own parts, through its scope. Under it, the two facts that trip people up: `get` on a group or a kind reads the first matching part; a part that sees has no distance output, read `contacts`.
- **A click on a part of the board** puts its id in the code as a quoted string (bare, when the caret already stands between quotes).
- **You can use** (below it): the whole script API as a clickable list with one plain line each, from ONE table (`SCRIPT_API` in `builder/scriptRef.ts`) that completion and the hover help in the code read too. A section the robot cannot use is dimmed with the reason, decided from the part definitions: Seeing when no part has a `sensor` or `radio` block, Messages when the robot has one core and builds nothing.
- **Checks as you type**, as a mark in the margin, an underline, and a list under the code where a click shows the spot: the sandbox's own answer (a syntax error with its line, or a throw as the script starts), then the pure checks of `sim-core` (`scriptChecks`: a name that reaches nothing with the real names, an unknown input or output with what the part really has, `contacts` or `scan` with nothing that sees, no `tick()`). A wrong name or input offers the real ones as one-click fixes that keep the quotes.
- **Completion**: inside `set("` and `get("` this robot's real names (groups, kinds, single parts), then after the name that name's real inputs (and for `get` what it reports); after `self.` and `keys.` their members; for a bare word the API's names, dimmed where the robot cannot use them. `Ctrl+Space` asks for it anywhere.
- Params are under the code as plain numbers; their sliders are on the card.

## Placing a saved blueprint (M7)
- The palette's **Blueprints** section lists every saved blueprint except the open one. Click one to hold a copy (with its scripts); the ghost shows every part it adds, red where a click would be refused (an overlap). `R` and `Shift+R` turn it, `F` flips it left to right, a click places it as one undo step, and it stays held for the next one; `Esc` or picking a part lets go. In mirror mode a click also places its mirror image across the axis.
- Placed, it is ordinary parts of this robot (Logan: copies, never links). Editing `missile.json` later changes nothing already placed. Its parts carry the tag `missile1` (then `missile2`), and its core keeps its own controls (`02`, Placing).
- Erasing the main core hands the robot to the next core (the first one left, in part order), and that core's controls with it (review E3): its bindings and scripts move to the main core's, after the ones already there, and its own entry goes. A binding both had is kept once; a script id both had gets a new name (`guide-2`) that the moved bindings follow. A placed copy's bindings get its scope on their targets (`burn` becomes `missile1.burn`), so they still mean its own parts; the code of its scripts is not rewritten, so a script that names the copy's tags needs the scope added by hand.
- **Controls for:** when the robot has more than one core, the Controls and Scripts panels get a picker: main core, then each other core by its scope (`missile1 (core@8,6)`). Picking a core shows and edits its own bindings, auto controls switch, and scripts ("on at release" instead of "on at deploy"); binding targets are that copy's own tags. Adding controls to a core that had none (a key, a script, a behavior from the shelf) gives it a `cores` entry. Moving or swapping the picked core keeps the panels on it under its new id. The script editor edits the picked core's script, so two missiles' `guide` scripts are separate, each saved to its own file (`launcher.missile1.guide.js`).

## Helpers
- Mirror mode (`M`): everything placed, swapped, moved or erased is mirrored across a vertical axis, with thrusters, wheels, and decouplers flipped to match, both sides or neither (see The board). The axis defaults to the core's column and can be shifted by half cells (`[` and `]`).
- Live stats: part count, total mass, and the center of mass drawn as a marker on the grid, updating as you build.
- Live validator: the issue list updates on every change; bad cells are outlined, and clicking an issue highlights its part.
- Bindings panel: add, edit, and remove key bindings (key, mode, target tag, channel, value). Data only until M3 makes keys do something.
- Not in M2: an ASCII text box (clunky for people; the grid text stays the format for files, the CLI, and Claude), and a test drop inside the builder (deploy is fast enough).

## Deploy
Three steps, per Logan:
1. Click **Test** (it was Deploy). Validation errors block it and are shown.
2. If there are unsaved changes (M16): a small box at the button says "Not saved." with three choices: **Save and test**, **Test anyway**, **Cancel**. `Enter` means Test anyway and never saves, whichever button has the focus; `Esc` or a click elsewhere cancels. There is no "don't ask again". Save and test goes on only when the save went through. With nothing unsaved, Test goes straight through.
3. The world opens with a ghost of the robot on the cursor (primary core on the cursor, mid-air allowed). Click to drop it; overlapping anything is refused; `Esc` cancels.
4. (M8, Logan) While the ghost is held, `F` flips it left to right and `R` turns it a quarter turn counterclockwise (the builder stamp's keys; they do not reach the robot you are driving). The world bar's **Team** button (Yours, or Enemy in red) sets its team. All three stick for the next deploy, saved in the browser. The deploy records the flipped and turned blueprint (`orientBlueprint` in `sim-core`), so replays need nothing new. Flipping keeps tags and scripts as they are, as the builder's mirror does. The flip is across the middle of the root part's cells (its own column for a one-cell root, between the two columns of a cannon), so the root stays where it is and flipping twice gives the same robot back (review E5).

Robots are deployed only from the builder (Logan declined a quick-spawn menu in the world for now).

## The live readout (M16)
In the world, bottom left, for the robot you control or watch. It replaced the script log panel. Folded, it is a small tab that says how many scripts run, or which one stopped and at which line; open (it remembers which, in the browser) it shows:
- each script running, off or stopped, with the message and the line of a crash; the keys it reads ("reads W A S D": every key it has asked about with `keys.down`, `pressed` or `released` since it was switched on, so a key it reads only with a param set a certain way shows only then); what it set this tick (its writes to single parts folded by kind: "throttle on 4 propellers: 0.52 to 0.56"; a name that reaches nothing is said); and its last four `log()` lines;
- **who drives what**: for each input a key is bound to or a script wrote, one sentence, keys first: "W is held: the key's 100% beats hover's 54%.", "hover sets it: 54%. W would take over.", "Nothing drives it now: it rests at 0%." Parts driven the same way are one line. Above them, for the robot you control, each held key a running script reads, said plainly: "W is held: hover reads it." (Logan: if a key is being read, no matter who reads it, he wants to know.)
- Nothing in it can be changed: settings are set in the builder (`04`, Decisions before M5). It is made from the world's trace (`04`, The trace), which the app asks for only while the readout is open, a few times a second.
- A part a behavior owns has its auto keys off, so with Hover alone no key is ever shown beating it (Hover reads W A S D itself, and the readout says so). A key shows up against a script when it is bound to an input the script also writes: a key of your own, or a part whose auto keys are switched back on.
